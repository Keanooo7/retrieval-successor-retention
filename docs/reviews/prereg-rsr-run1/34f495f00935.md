## (b) The tie rule (A3c.2)

At `6267fd6` (`run.py:2267-2275`):

```python
arm_status = {a: arm_outcome(v["rc"], v["hb"], v["result"]) for a, v in arms.items()}
bad = [(a, o) for a, o in arm_status.items() if o[0] != int(Exit.OK)]
if bad:
    for a, (_code, _status, note) in bad:
        doc["notes"].append(f"{note}: {a}")
    a, (code, status, _note) = max(bad, key=lambda x: EXIT_RANK[x[1][0]])
```

- **`arms` is built in `ARMS` order**, which is (psiC, fifo, age). Python's `max` returns the
  *first* maximal element, so the arm tie rule is "first in psiC, fifo, age" exactly as registered.
- **Every non-OK arm's note is appended before the selection**, so "the note lists every non-OK
  arm" is true at `6267fd6`. T17 still lists it as TO-CONFIRM, which is redundant but harmless.
- **`EXIT_RANK`** (`:995-1000`) is INERT 3 > DID_NOT_RUN 2 > FAIL 1 > OK 0, which is A3b.5's order.
- **Across seeds**, `finalize` takes `max(docs, key=(EXIT_RANK[exit], -seed))`, so ties go to the
  lowest seed (`:2427`).

*Nit:* `arm_outcome` (`:1003-1016`) labels an arm with rc 0 whose result cannot be parsed
`crashed` (it falls through). That is a rare mislabel. The exit is 3 either way.

## (c) A3c.4 against R-2026-09-22-inert-exit-5:21

The ruling (main), line 21: "inconclusive — otherwise (the 0.01–0.1 band) | `1 FAIL` — liveness not
demonstrated; the ledger records the band label. Never `0`, never `5`." A3c.4 maps a C5-read
`inconclusive` with training rc 0 to `failed`, exit 1, with a `LIVENESS_INCONCLUSIVE` note. That is
the ruling's code, and `ledger.py`'s only defined status. It is consistent, and it closes the "fall
through to `ok`" hole. The harness does this at `6267fd6` (`run.py:2290-2294`).

**MINOR-A3c-1. Within a seed, the harness can rank exit 1 above exit 3.** In `measure_seed`
(`run.py:2288-2297`, `:2359-2366`):

1. C5 inert returns 5;
2. then C5 inconclusive returns **1**;
3. only *after* that does C6 return 3;
4. and the C1, C10 (and later C2–C4, C7, C8) failures return 3 at the end.

So if C5 reads `inconclusive` **and** C6 or C10 fails, the seed exits **1** (`failed`). A3b.3 says
"measure-seed takes the worst arm by this table, using the A3b.5 order", under which 3 > 1.

- The case is unlikely: train() itself already exits 1 for inconclusive, so A3c.4's case "should
  not arise" at all.
- *Fix:* when the harness is next touched (T15/T17), evaluate the inconclusive branch after C6 and
  after the post-training controls, or take the max over all outcomes.
- The PREREG could also say explicitly that the A3b.5 order spans arm outcomes **and** control
  failures within a seed. A3b.3's table implies it but does not say it.

**On `srep_norm_reg_weight` = 0.0, the PM's substrate-fidelity decision: it is not an owner item
for run 1.**

1. It is not a registry constant (MEASURED, DERIVED, CONDITIONAL or FROZEN). No ruling,
   correction or ADR reserves it. The scope ruling's D2(b) fixes the freeze, not the hinge weight.
2. Under that freeze it changes no update, as shown in §a. It changes only an unread field (`loss`)
   and the config hash. No run-1 number the PREREG reads (`loss_lm`, accuracy, NLL, L_MC,
   diagnostics) depends on it.
3. 0.0 is the value the substrate was actually trained under. This is arm B's `result.json`
   config: `srep_norm_reg_weight` 0.0, while `tg.srep_norm_reg_weight` 0.01 was not used. The
   choice removes a recorded mismatch without changing any outcome.

**Where it would become owner-level.** Correction 15 item 4 / RESEARCH-CONTEXT §10.1 defect 3 say
the hinge is part of TG's loss. Arm B's lineage trained with it off. For an **unfrozen** successor
(the D2(b) "training continues" arm), 0.0 against 0.01 is a choice of objective with real
consequences, and D2(b) says that arm is "pre-registered before it runs".

**MINOR-A3c-2.** A3c.1 reason 3 (`PREREG:2685-2687`) argues for 0.0 partly to avoid a *silent*
0.01 in a successor that copies this command line. Copying run 1's command would, however, give the
successor a silent **0.0**. Amend the wording, or add a sentence, so that the successor's weight
must be chosen explicitly in its own PREREG, and arguably put to the owner. It must not be
inherited from run 1's launcher in either direction. No run-1 change is needed.
