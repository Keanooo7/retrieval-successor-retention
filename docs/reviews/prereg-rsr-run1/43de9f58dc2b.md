**MINOR-A4-1, the RNG note.**

- The checkpoint's `rng` record has five entries. `cpu`, `cuda` and `mps` are equal. **`python` and
  `numpy` (the global `random` and `np.random` states) differ** between cadences, in the author's
  pair as in mine.
- So A4.2's "`RNG (2)` all `torch.equal`" and "writing a checkpoint perturbs neither the RNG …" are
  slightly too strong. Saving a checkpoint moves Python's and NumPy's global RNG state; I did not
  identify which call does it.
- **It is harmless here.** Training never reads those streams: every training output above is
  bitwise identical, and so is the end-of-run liveness ratio. The harness's references and bootstrap
  use dedicated `torch.Generator`s. Resume, which would restore these states, is forbidden.
- *Fix:* the wording ("the torch, data-order and φ streams are unaffected; Python/NumPy global states
  differ and are unused"). No design change.

**The step-160 reading is DIAGNOSTIC only.**

- `PREREG:3202-3203`: "Every step-160 number is labelled DIAGNOSTIC. It is never the headline,
  never gated, never read against a threshold, and never used to revisit R-1".
- `PREREG:3398-3399` (T19 item 6) says the same for RESULTS and the ledger.
- The headline remains psiC − fifo at the final step (A1.4).

**Reusing the φ-free passes is sound.**

- `fifo`, `oracle`, `lru`, `random0–4` and `sz_fifo` read the fifo arm's model and no φ.
- The transformer is frozen in every arm, and C3 checks the read checkpoints equal the substrate. So
  the model at step 160 is byte-identical to the model at 3000.
- With O5 = eval there is no dropout, and these policies hold no learned state.
- Their per-document records are therefore exactly what a re-run at 160 would produce.

Only the φ-reading passes (`psiC@160`, `age@160`, `sz_psiC@160`, `sz_age@160`) need re-running, as
registered. Reusing the same bootstrap matrix `W` (generator `20260927 + seed`) keeps step-160 and
final contrasts on the same replicates. That is fine for DIAGNOSTIC use.
