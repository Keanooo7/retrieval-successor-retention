## (d) Status mapping

**`ledger.py:101-105`.** "failed" is "a run that completed and whose own pre-registered check
failed, exit 1". No other status is defined in the file.

**Run 1's exit codes.** A failed control is exit 3 and inert is exit 5, under
`R-2026-09-22-inert-exit-5` ("a control fails / … / measurement raised → `3 DID_NOT_RUN` — the
measurement is not valid"). Writing `"failed"` (the harness at `58d25cc`) therefore contradicts
the ledger's own definition. A3.11 is right to avoid it.

**`partial` for a completed run with a failed control** is consistent with the vocabulary, but it
stretches the word. In repo usage `partial` means:
- a run stopped before completion (`experiments/capacity-c0/run.py:1842-1843`, "any stop before
  completion is partial"; `experiments/scaffold-timing/run.py:1149`);
- or an inconclusive comparison (`scripts/canary.py:378`, `:399`, exit 2).

Nothing gates on the difference: `scripts/orchestrator/lanes.py:291` treats every non-`ok` alike. It
is defensible as "results exist; not all valid". `did_not_run` would match exit 3 literally, but it
would hide that training ran.

**The B2 precedent is mis-cited and is mixed.** `experiments/b2-psi-probe/run.py:2220` (at
`night/2026-09-30`) is inside **`run_size`** (`def` at `:2108`), the sizing step, not phase A. There
`partial` goes with exit 3 when its controls are not ok. **B2's phase A (`run_fit`, `:3547`) and
phase B (`:3637`, `:3658`) write `"failed"` with exit 3** on child or control failure, the same
ledger-inconsistent usage A3.11 now avoids. So B2 supports `partial`+3 only in sizing. See
MINOR-A3-1.

**Inert maps to `partial`, exit 5, with an `INERT` note.** No status names inert, and I found no
experiment precedent. The exit code carries the routing (the ruling routes on the code), so this is
consistent.

**MINOR-A3-2.** A3.11 maps "an arm's training rc is not 0" to `crashed`. Under the per-job reading
rule (A1.2, A2.3), an arm with rc 1 and a `completed` footer whose liveness band is `inconclusive`
did not crash. `measure_seed` labels it `crashed` (`run.py:2186-2187`). A label such as `partial`
with a note `LIVENESS_INCONCLUSIVE` would be accurate. The exit code (3) is right either way.

## (e) T7 restated

**Accurate, and reproduced.** My own loop (`a3/t7_review.py`, calling `OraclePolicy` directly on
the seed-0 pool) exited with rc 0:

```
gamma 1e-08: g**38 = 1.0000000000000008e-304  g**39 = 1e-312  g**46 = 0.0
gamma 1e-10: g**38 = 0.0  g**39 = 0.0  g**46 = 0.0
max exponent q-t-1 over pending asserts at any eviction (seed 0 pool): 30
gamma 1e-08 vs 0.9: decisions differing 0, documents 0
gamma 1e-10 vs 0.9: decisions differing 0, documents 0
gamma 1e-11 vs 0.9: decisions differing 0, documents 0
gamma 1e-12 vs 0.9: decisions differing 24, documents 1
gamma 1e-300 vs 0.9: decisions differing 5487, documents 247
```

The 1e-12 and 1e-300 counts equal A3.15's exactly (`PREREG:2189-2190`).

**MINOR-A3-5, wording only.** "As long as the powers γ^k, **k ≤ 46**, do not underflow"
(`PREREG:2195-2196`) is a sufficient condition, not the operative one.

- At γ = 1e-8, γ^46 is already 0.0, yet decisions are identical.
- The exponent that matters is q − t − 1 for an assert still pending at an eviction. That is
  ≤ max_gap − 2 = 38 by construction, and 30 at most on the seed-0 pool.
- Underflow changes a decision only when an underflowed pending assert ties at 0 with a lower-index
  zero-demand slot. That is why 1e-10 and 1e-11 survive and 1e-12 does not, here.

A tighter statement: invariant if γ^38 > 0, observed down to 1e-11 on this pool. It has no
consequence for γ_o = 0.9 or C9's 0.5.

### MAJOR

**MAJOR-A3-1. A leaked `DRY_RUN=1` disables launcher v3's whole environment guard. A3.8's "the
launcher refuses with rc 3 and nothing starts" is false for it.**

The evidence is in §b: the tmux client-environment leak, measured.

- Dry runs set `DRY_RUN` together with `RSR_ORCH_ROOT`, `OUT` and `JOB_SUFFIX` (A3.7's own probes
  did). A shell that leaked the latter three (review MINOR-A2-3) leaks `DRY_RUN` too.
- The launcher then starts nine full-length jobs in a foreign lane root, outside the shared lane
  accounting, beside the battery.
- They are rejected only after training: by C10, by `measure-seed`'s missing `launch-git.json`, and
  (after T16) by `dry_run` itself.

*Fix (Amendment 4, launcher v4), either:*
- (i) refuse `DRY_RUN=1` unless `STEPS=0`, so a dry run can never train; or
- (ii) have the A3.8 tmux command start the launcher under
  `env -u DRY_RUN -u OUT -u JOB_SUFFIX -u RSR_ORCH_ROOT -u CKPT`.

(i) closes the hole at the source. (ii) keeps the author's `STEPS=3000` CKPT probes possible, which
had no `.venv`. Either way, correct A3.8's sentence and keep T16 (C10 rejecting `dry_run`).

### MINOR

- **MINOR-A3-1. The B2 citation in A3.11 is wrong.** `run.py:2220` is in `run_size` (sizing), not
  phase A. B2's phases A and B write `failed` with exit 3. Cite `run_size` and say the precedent is
  mixed (§d).
- **MINOR-A3-2. A liveness-inconclusive arm is labelled `crashed`.** See §d.
- **MINOR-A3-3. C9/C9b tagging is incomplete at `58d25cc`.** The oracle's accuracy column in the
  held-out table and the ledger's `oracle_regret.*` and `headroom_share.*` rows are not tagged when
  C9/C9b fail. A3.6 requires both. Make sure T15 covers the ledger, not only RESULTS.
- **MINOR-A3-4. `finalize`'s status can disagree with its exit.** It takes the *first* non-OK
  seed's status (`run.py:2317-2319`), while the exit is the *worst*. For example, seed 0 `crashed`
  (3) and seed 1 inert (5) gives exit 5 with status `crashed`. A3.13 says "Its status is that
  seed's", meaning the worst. Align the harness, or state the tie rule.
- **MINOR-A3-5. T7's "k ≤ 46"** is a loose sufficient condition. See §e.
- **MINOR-A3-6. JSON hand-assembly in the launcher.** `launch-git.json` is built by string
  interpolation (`PREREG:1991`). A `"` or `\` in any recorded value would make it invalid JSON, and
  `measure-seed` would then fail to parse it. The current values cannot contain those characters
  (fixed flag spellings, absolute paths), so the risk is low. Not measured.
