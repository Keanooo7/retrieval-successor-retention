## Rulings on the seven flagged items

### 1. δ is undefined — LAUNCH-BLOCKING (finding B-1), and the amendment cannot reach the harness as written (B-2)

Confirmed: run 1's PREREG says "it uses no δ" (`experiments/rsr-run1/PREREG.md:304`), so
§7.2's TIES (`PREREG.md:271`) is undefined and `evaluate` refuses (`run.py:561-565`). Correct
behaviour, and by definition launch-blocking for EVAL.

**Is B2's δ well-defined for run 1's EVAL set?** B2's rule (`b2-psi-probe/PREREG.md` §9.3, A1.11)
is `δ_s = 0.25 × (acc_oracle(all) − acc_FIFO(all))`, γ_o = 0.9, all-query accuracy read through
the model, **on FIT_VAL `[936000, 937024)`, "never on EVAL"**. Its measured values at ckpt3000
(`RESULTS-phaseA.md:146`) are **0.038022 / 0.036757 / 0.031858**. Same substrate as run 1 and
this referendum (B2 §2 pins the same three sha256s: `0ee3f8a6…`, `dadd1e08…`, `b507ebc5…`), same
`M = 16`, `S = 48`, the same oracle construction at γ_o = 0.9 (run 1 A2.2), the same pooled
all-query statistic as this run's headline. All three are > 0, so B2's "δ ≤ 0 → undefined"
branch never fires.

The PM's sentence admits two readings, and they are not equivalent:

- **(a) B2's values, applied per seed to the ES − ψC CI on run 1's EVAL documents.**
  Well-defined now, before any referendum data. Faithful to B2's own rule (δ from a non-EVAL
  split). Needs no new measurement. **Recommended.**
- **(b) The rule recomputed on run 1's EVAL `[995000, 997048)`** from run 1's `oracle` and
  `fifo` held-out passes. Computable once run 1's measure-seed writes them, but: it contradicts
  B2 §9.3 ("never on EVAL"); δ would be undefined at any seed whose C9/C9b fails (run 1 A3.6
  marks oracle-derived numbers not read); the values could only be written after run 1's EVAL
  accuracies are seen; and the harness has no code to compute it. **Not recommended.** If
  the PM nevertheless wants (b), the amendment must say so explicitly, name the C9/C9b and
  δ ≤ 0 fallbacks, and `finalize` must compute δ from the record files, not from a typed table.

### 3. The Recorder adapter — correct; it cannot alter a reported number

`es_recorder()` (`run.py:316-326`) swaps `Recorder` in the run-1 module object that this
harness loaded (`_es_ref_rsr_run1`). `run_batch` resolves `Recorder` from its module globals at
call time, so the swap takes effect, and `finally` restores it. `ESRecorder.memory_weight`
forwards its arguments unchanged. Its only side effect is an int attribute on the policy, which
is not a parameter or buffer and so stays out of the state dict.

Everything else is inherited: eviction recording, `on_write` residency, `needs_eval_context`
(False for Expire-Span, so `eval_capture` never raises). E7 checks `S` calls per batch, and
E8 checks residency against the model-free replay. Without the adapter the pass would run
unmasked, so the adapter is necessary. Run 1's live harness runs in another process and is
unaffected. One test-strength gap: F-6.

### 5. The init handicap, one config across seeds, and SUPERSEDES first — none is launch-blocking

**F-2 (FOLLOW-UP, owner-visible), the init.** At init 0.1 a memory gets zero attention past
age 0.1·L + R (4.16 / 8.32 / 12.48), where the frozen substrate was trained reading 16 FIFO
slots.

[P7]'s stated reason for a negative b is GPU memory (P7:L1011-1015; P7-verification 7a).
That reason does not apply under a hard `M = 16`. So the handicap is the port's
(`expire_span.py:170-174` hard-codes `< 0.5`), not something [P7] demands.

Recovery is plausible within the budget, but this is not measured. Adam at lr 1e-3 moves b by
at most ≈ 3 in 3000 steps: σ ≈ 0.69, so e ≈ 22 at L = 32 and 33 at L = 48, beyond FIFO's
16-step horizon. `w` adds more capacity. At L = 16 the span can never exceed FIFO's horizon.

It is pre-registered and declared (§11.4), and it biases against Expire-Span, which is the
direction B-3 forbids. But it is not a defect under policy §3. **Fix:** RESULTS reports each
selected config's per-layer `e` at step 3000 (already logged as `es_bias` / `es_weight_norm`)
against the 16-step horizon. A LOSES or MIXED class is reported as "at [P7]'s code
initialisation 0.1, 3000 steps". Brendan sees this caveat beside any non-SUPERSEDES outcome.

**One config across seeds (§6.3): FOLLOW-UP, no change recommended.** It is pre-registered,
exact, and ties to the lowest row. It is less optimistic than per-seed selection on 512 VAL
documents.

**F-3 (FOLLOW-UP, owner-visible), SUPERSEDES first.** This is the PM's verbatim text, applied
in B-3's direction. It is implemented and tested (`run.py:610-616`;
`test_supersedes_takes_precedence_over_ties`). Note for Brendan: unlike B2's WIN, SUPERSEDES
has no effect-size floor. A CI inside `(0, δ]` on all three seeds triggers falsifier 6.

### 7. Suite note — cause confirmed; FOLLOW-UP (I-tier)

`measure_seed` reads `job_record(cfg, a)` from `cfg.orch_root`, which defaults to
`SHARED_ORCH_ROOT` (`experiments/rsr-run1/run.py:349, 767-775, 2853`). Outside `--dry-run` it
ignores `RSR_ORCH_ROOT` (`:2796-2802`). So the session `e2e` fixture (`tiny_cfg`, no
`orch_root`) picks up the live run's `rsr-run1-<arm>-s0.json`, and C10 compares the fixture
against run 1's real argv.

Measured: with only the shared-root reads redirected to an empty directory, the file is
**97/97**. The 7 failures are environmental, not caused by this branch.

**F-4 (FOLLOW-UP, I-tier):** pass `orch_root=<tmp>` in `tiny_cfg` (or the `e2e` fixture), so
the file never reads the shared jobs. This is a test-only change on the run-1 harness tests.
