**Verdict: DO NOT MERGE.** 1 BLOCKER, 2 MAJOR, 6 MINOR.

The driver's merge logic is sound. I found no path by which a mutation ends up PROVEN, or missing,
without its shard having finished it. The blocker is outside the merge logic. The author's
"unexplained flake" has a cause, which I reproduced: git worktree administration is not safe under
concurrency. The flaky test then sits inside the suite that every battery runs about 381 times, and
there it produces wrong verdicts: a spurious undeclared red that marks an unrelated mutation LEAKS.

## BLOCKER-1: the e2e flake is a git worktree race, and inside the battery's suite it produces false LEAKS verdicts

**Where:** `scripts/battery_isolation.py:311-317` (`_registered`), `:337-340` (`worktree add`), `:350-355`
(`worktree remove`) and `:422-426` (the teardown in `open_pool`'s `finally`). These are driven
concurrently for the first time by `scripts/battery_shards.py:446-473`. They are exercised by
`tests/test_battery_shards.py:673` (`test_sharded_verdicts_equal_the_serial_ones_on_the_stub`) and, on the
same race, `:716` and `:730`.

**Cause, reproduced (not suspected).** I ran 300 runs of the e2e test in a scratch clone at c4a2dc0, as
6 parallel loops of 50. **2 of 300 failed.** Both failing runs' shard logs, which commit c4a2dc0
correctly added to the failure message, say:

```
--- shard 1 of 2 log ---
DID NOT RUN: not isolated: git worktree list -> rc=128: fatal: Invalid path '/private/var/folders/.../pytest-7877/test_sharded_verdicts_equal_th0/stub/.git/worktrees': No such file or directory
...
LEAKS         leaks                                      -> 1 on gate, 1 off (1 undeclared)
```

(`scratchpad/flake-3-12.log` and `flake-6-3.log`.) Shard 1 had already scored its mutation (the `LEAKS`
line). Then its teardown's `_prune_unlocked` → `_registered` ran `git worktree list`. At that moment
shard 0's `git worktree remove` had removed the stub's last worktree, and git `rmdir`s an emptied
`.git/worktrees`. `_ok` raised `Unisolated` inside `open_pool`'s `finally`, before `_report` wrote the
rows. The battery refused 3, and the shard's finished rows were discarded.

Plain git on a scratch repo, with git 2.55.0 (`/opt/homebrew/bin/git`), fails the same ways:

- **4 loops of worktree add and remove, 500 each, on one repo:** 3 adds failed. One failure was
  `fatal: could not create directory of '.git/worktrees/shard-0': No such file or directory`, another
  loop's `rmdir` of the empty `.git/worktrees`. Two were `fatal: failed to read
  .git/worktrees/shard-0N/commondir`.
- **Real-repo topology** (one permanent worktree, so `.git/worktrees` never empties): 6 simultaneous
  `git worktree add` calls, like N=6 shards starting, gave **4 failed adds out of 360 (60 rounds)**.
  Three later runs of 200 rounds each gave 2, 4 and 5 failed adds out of 1200, each
  `fatal: failed to read .git/worktrees/shard-0N/commondir`. That is roughly 2–7% of 6-shard starts
  losing a shard. `git worktree list --porcelain`
  failed **4 times out of 1500** while other processes added and removed worktrees, each
  `fatal: failed to read '.git/worktrees/shard-0/locked'`.

**Why this blocks: a wrong verdict, not a nuisance.**

1. *Inside the suite.* `tests/test_battery_shards.py` runs in every battery's suite, both baseline and
   per mutation, about 381 times per battery at 380 entries. A spurious red of the e2e test:
   - on the baseline, refuses the whole battery with "suite is not green before mutating";
   - on a mutation whose gate goes red, adds an **undeclared off-gate red, so the verdict is LEAKS**.
     The author's own log already holds this case: `I2-build.existing-mutations-vs-new-tests.log:769-773`,
     `C0: two jobs given the same out_dir`, reads `RED off gate (UNDECLARED): ... test_sharded_verdicts_equal_the_serial_ones_on_the_stub`.
     The 3 e2e tests are declared only on the ~15 entries that couple to them, not on the other ~365.

   Measured per-run rates are about 1/500 (the author, at ordinary load) and 2/300 (mine, 6-way load).
   At 381 suite runs that is 1−(1−p)^381 ≈ **53% to 92% of batteries carrying at least one false
   red**. This is an extrapolation from measured per-run rates, not a measured battery. It applies to
   the **serial** battery too, not only to sharded ones.
2. *On the real repo, the sharded driver itself.* N shards start at the same instant and each runs
   `git worktree add`. At N=6 the simulation lost a shard at startup in roughly 2–7% of rounds. A teardown `git worktree list` that overlaps any other worktree operation (another shard, the
   serial battery's default pool, an agent creating a worktree) discards that shard's whole slice after
   it ran, at about 60 mutations × 2.4 min at N=6. That part is fail-closed (DID_NOT_RUN), but it makes
   the I2 N∈{1,2,4,6} measurement and the serial-equals-sharded proof unreliable to complete.

**Fix.**
- Serialize worktree administration across processes. In `battery_isolation`, take an exclusive `flock`
  on one repo-wide lock file in the git common dir (e.g. `<common_dir>/rsr-worktree-admin.lock`) around
  `worktree add`, `worktree remove` and `worktree list` (`make_shard`, `remove_shard`, `_registered`).
- Add a mutation for that lock, since the house rule is one mutation per check.
- Then re-run a loop of at least 300 e2e runs at 6-way load and record the log, with 0 failures
  expected.
- Separately, for the owner of I1: a teardown that cannot *list* worktrees should not throw away rows
  that were already scored. Log the prune error rather than raise it in the `finally`.

**Re-run it (about 10 s, touches no repo; paste into zsh):**

```zsh
G=/opt/homebrew/bin/git; T=$(mktemp -d); cd $T
$G init -q r && echo x > r/f && $G -C r add f && $G -C r -c user.email=a@b -c user.name=a commit -qm x
$G -C r worktree add -q --detach $T/perm HEAD
for r in {1..200}; do
  for k in 0 1 2 3 4 5; do ( $G -C r worktree add --detach $T/s/$r/p$k/shard-0 HEAD >/dev/null 2>>$T/err || echo F >> $T/fail ) & done; wait
  for k in 0 1 2 3 4 5; do ( $G -C r worktree remove --force $T/s/$r/p$k/shard-0 2>/dev/null ) & done; wait
done
echo "failed adds: $( [ -f $T/fail ] && wc -l < $T/fail || echo 0 ) / 1200"; grep fatal $T/err | sed 's/shard-0[0-9]*/shard-0N/' | sort | uniq -c
```

Expected output: a non-zero count (2, 4 and 5 in my three runs) and
`N fatal: failed to read .git/worktrees/shard-0N/commondir: Undefined error: 0`.

## MAJOR-1: the serial-equals-sharded e2e assertion fails as soon as I6 lands, and not because of shard paths

**Where:** `tests/test_battery_shards.py:696` (`assert json.loads(merged) == json.loads(serial)`) and
`scripts/battery_shards.py:234` (`os.environ["RSR_BATTERY_THREADS"] = str(args.threads)`).

I built a scratch clone at I6's pushed head `41db09d`, added I2's three new files, and wrote
`mutation_battery.py` with `battery_union.union(898628a, 41db09d, c4a2dc0)`, called in-process.
Running `tests/test_battery_shards.py tests/test_battery_env.py` there gave rc=1,
`passed=61 failed=1`:
`FAILED tests/test_battery_shards.py::test_sharded_verdicts_equal_the_serial_ones_on_the_stub`, with the
merged row carrying `'rsr_env': {'RSR_BATTERY_THREADS': '1'}`. The I6 author's own combination at
their unpushed 3589917, which normalizes the paths, fails the same way (`I6-fix2.36-i2-combo-rowdiff.log`):

- serial `rsr_env {}` vs sharded `{'RSR_BATTERY_THREADS': '1'}`;
- serial `rsr_env_suite` lacks, and sharded has, `RSR_BATTERY_THREADS` and `RSR_TORCH_THREADS`.

The difference comes from I2's own `run_shard` env write, not from shard location. I6's path
normalization cannot remove it, which contradicts the premise that I6 alone makes rows
shard-independent.

Beyond the stub, `failure_reasons` carry per-run paths such as `pytest-of-keanooo7/pytest-NNNN/...`, and
shard roots inside `Unisolated` messages (see the author's proof log, e.g. line 92 of `I2-build.md`).
So whole-row equality fails between *any* two real batteries, serial or sharded. The requirement's proof
("identical per-mutation verdicts") needs a defined projection, and the branch defines none (the
author's open questions 3 and 4).

*Does I2 mis-merge rows with extra keys?* No. `row_problem` (`battery_shards.py:300-311`) checks only
for **missing** serial fields, so `rsr_env` and `rsr_env_suite` pass through untouched. Verdicts are
unaffected. See MINOR-4 for the rows I2 synthesizes.

**Fix.**
- In the e2e test, run the serial arm with `RSR_BATTERY_THREADS=1` as well, so both arms run under one
  recorded environment.
- Compare a verdict projection: `mutation, gate, verdict, reddened_gate, n_on_gate, off_gate,
  off_gate_undeclared, off_gate_allowed`.
- Put that projection in `battery_shards.py` (e.g. a `compare SERIAL SHARDED` action that exits 0, 1 or
  3), so the later proof uses the tested definition rather than an ad-hoc diff.

## MINOR

1. **`battery_shards.py:387`.** `--slots "1"` is hard-coded, while `--threads T` is passed through
   (`:380`). With `--slot-wait S --threads 4`, one cpu-det slot is reserved but the suite runs at 4
   threads, because `RSR_BATTERY_THREADS` overrides the slot's thread env in `_suite_env`. I checked
   this in-process: `launch(..., threads=4, slot_wait=10)` produces `--slots 1` and child
   `--threads 4`. *Fix:* pass `--slots str(threads)`, or refuse `threads != 1` together with
   `--slot-wait`.
2. **`battery_shards.py:394-410` (`_prepare`).** There is no whole-table anchor check before any shard
   starts. A stale anchor refuses only the shard whose slice holds it, while the other N−1 shards run for
   hours toward a result that exits 3 anyway. The serial battery checks every anchor before its first
   suite (the 2026-09-22 lesson, `mutation_battery.py` `main`). The comment at `:439-440` ("refused by
   every shard's own battery") overstates this: only one shard refuses. *Fix:* call
   `mb.anchor_problems()` in `_prepare` and raise `Refused`.
3. **Two checks no test covers.** My ad-hoc mutations on the I2 test file:
   - removing the gate comparison in `row_problem` (`:303`) left `passed=44 failed=0`;
   - removing `isinstance(rc, bool)` (`:288`) left `passed=44 failed=0`.

   Both are redundant given the table fingerprint and the int-typed done record. *Fix:* delete them, or
   test and mutate them. The house rule is one check, one gate.
4. **`battery_shards.py:337`.** The `DID_NOT_RUN` rows that I2 synthesizes via `mb._row` lack I6's
   `rsr_env` and `rsr_env_suite`, so once I6 lands the merged record is heterogeneous. I6 documents the
   keys as being "on every row of the `--json` record". *Fix:* at integration, either stamp synthesized
   rows with `null`/`{}` or document the exception.
5. **`battery_shards.py:227`.** The done record's `sha` is a separate `git rev-parse` from the battery's
   own `iso.pinned_sha` in `open_workspace`. A commit landing in the invoking tree between the two
   reads, a window of milliseconds, would record a SHA the battery did not run. *Fix:* re-read HEAD after
   `mb.main()` returns and require that it is unchanged, or record the battery's shard SHA.
6. **Cost.** 31 entries is about 74 min per serial battery at 2.4 min each. Some gates are defensive
   rather than evidential: `plan prints a merge for one shard`, `every shard has the same slot job id`,
   `shards are launched in the battery lane`, `shards run one after another`. Their gates are distinct
   (no duplicate gate, and each gate name matches exactly one test function). Trimming them is the
   manager's call, not a merge condition.

## Checked and found sound

- **Fail-open paths.**
  - A missing, stale, foreign, short, reordered or duplicate rows file, or a done record from another
    run id, index, N, SHA or table, each becomes `DID_NOT_RUN`. The checks are `shard_problem` and
    `row_problem` (positional name match).
  - Every index gets a row, because `merge_rows` iterates a validated partition.
  - `--shards 0`, a negative N, and N greater than the table are all refused with 3.
  - A shard killed after rows but before the done record is `DID_NOT_RUN`.
  - Exit 1 from a shard can only be a crash: shards run `mb.main()` **without** `--check`, so a
    finished battery returns 0 (LEAKS and ADDS NOTHING rows included) or 3. Rejecting rc 1 therefore
    hides no verdict. My ad-hoc mutation admitting rc 1 reddened
    `test_a_shard_that_exited_outside_0_and_3_is_did_not_run[1]`.
  - Two concurrent `run`s on one work dir: the I1 pool lock refuses the loser, and a done record naming
    the other run id makes the loser's merge `DID_NOT_RUN`.
- **Exit codes.** The 27 battery-referencing test files at head, including `tests/test_exit_codes.py`,
  gave rc=0, `passed=1198 failed=0 skipped=0 errors=0`.
- **Slot path.** `slot._parse(launch(2, 6, run, W, threads=1, slot_wait=3600, ...)[3:])` parses to lane
  `cpu-det`, slots 1, wait 3600.0, job id `<run>-s2of6`, with a correct child argv. `PYTHONPATH` gets
  `<root>/scripts` prepended and is stripped from the suite by `_SUITE_STRIP`. `ops/lanes.json` exists,
  with `cpu_det_slots` 12. A reused `--run-id` makes slot refuse with 3 on the existing job record,
  which is fail-closed.
- **The 7 declarations appended to I1 entries.** I cross-checked every declared `test_battery_shards`
  node on the 7 I1 entries and the 8 I2 entries against the author's four proof logs, and **each was
  observed red at least once**. None rests on reasoning alone (see MAJOR-2 for the report saying
  otherwise).
- **Union compatibility.** I called `battery_union.union` in-process with each branch's own merge base
  (B5's is `f7a6b10`) on scratch texts. All 6 orders of {I2, I6@41db09d, B5@deaeaa6} succeed with 396
  entries, and all 6 orders with I6@3589917 succeed with 399. I2 contributes +31 new entries and ~7
  updated ones, with no "both changed" refusal. A future branch that edits the `off_gate_allowed` of
  any of those 7 I1 entries will be refused and must be resolved by hand. That is disclosed and
  acceptable.
- **Anchors and names.** In-process, `mutation_battery.anchor_problems()` gives `[]`, and there are 380
  entries with 380 unique names.
