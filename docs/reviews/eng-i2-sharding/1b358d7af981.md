## MAJOR-1: `compare` exits 0 on rows that have no verdict fields (a 3 collapsing to 0)

**Where:**
- `scripts/battery_shards.py:401-404`: the only schema check is `isinstance(r, dict) and "mutation" in r`.
- `scripts/battery_shards.py:419-424`: every field is read with `.get()`, so a key missing from both
  arms compares `None == None`.

**Reproduced by hand** (in-process `bs.main(["compare", A, B])` on scratch files; log
`review2-i2/compare_probe.log`):

```
--- 3-no-verdict-fields                      # [{"mutation":"a"},{"mutation":"b"}] in both arms
compare: OK (0 line(s)) on mutation, gate, verdict, reddened_gate, n_on_gate, off_gate, off_gate_undeclared, off_gate_allowed
rc=0
--- 5-bool-vs-int                            # reddened_gate True vs 1, n_on_gate 1 vs True
compare: OK (0 line(s)) ...
rc=0
```

**Why it must change before merging:**

1. The author's report (`I2-build.md:221`) says that "a non-battery record" exits 3, and `compare`'s
   own refusal text is "not a battery --json record" (`:405`). A list of rows with a `mutation` key
   and nothing else is not a battery record, yet `compare` scores it **identical, exit 0**.
2. The merge path already refuses exactly this. `row_problem` (`:324-326`) marks a row lacking any
   field of `mb._row(m, {}, None)` as DID_NOT_RUN. `compare` does not reuse that check.
3. The manager decided that the later serial=sharded proof is judged by this tested `compare`.
   `rsr.exit_codes` names "3 collapsing to 0" as the way this design is silently defeated.
4. The realistic trigger is narrow: a wrong file passed as an arm, or a future row schema that renames
   a verdict field in both arms. But the fix is a few lines, and the instrument should not ship
   fail-open.

**Fix.**
- In `compare_rows`, return `Exit.DID_NOT_RUN` unless every row in both arms carries every field in
  `VERDICT_FIELDS` with the serial types:
  - `verdict`: a `str` in {PROVEN, LEAKS, ADDS NOTHING, DID_NOT_RUN};
  - `reddened_gate`: a `bool`;
  - `n_on_gate`: an `int` that is not a `bool`;
  - the three node fields and `off_gate_allowed`: `list`s.
- Add a test (the `[{"mutation": ...}]` case, plus bool vs int).
- Add one mutation for the new check.

**Where:**

  sits outside the `try`.
- `:381`: `remove_shard` now calls `admin_git`, which runs `worktree_admin_lock` → `common_dir(source)`
  at `:130`, which runs `_ok(...)` and **raises `Unisolated`**. On I1 (`898628a`), `remove_shard` used a

  "returns an error line or None". This is an I1 behaviour that did not survive.

**Reproduced by hand** (`review2-i2/teardown_probe.py`, stub repo, single process). `common_dir` fails
after the body has "scored". The pool's exit raises:

```
TEARDOWN RAISED over scored rows: Unisolated git rev-parse --git-common-dir -> rc=128: fatal: not a git repository ; scored = ['verdict']
left registered: [.../pool/shard-0, .../stub]
```

In `mutation_battery._run_isolated`, that escape happens before `_report`, so the battery refuses 3
with its rows unwritten. Commit 375f1ba's subject says this "never raises". The trigger is rarer than
the list race, e.g. a moved or removed invoking tree, a missing git, or an `OSError` opening the lock
file.

**Fix.** Either:
- in `teardown`, catch `(Unisolated, OSError)` around each `remove_shard` as it already does around
  the prune; or
- resolve the lock path once in `open_pool` and pass it down, so `remove_shard` cannot raise.

Extend `test_a_teardown_that_cannot_list_worktrees_keeps_the_verdicts` with a `common_dir` or
`remove_shard` failure.

## MINOR-2: `compare` hides a real difference behind any DID_NOT_RUN row

**Where:** `scripts/battery_shards.py:416-418`. The DID_NOT_RUN return comes before the diffs are
computed.

**Reproduced by hand** (`compare_probe.log`, case 4). In the sharded arm, mutation `a` is
DID_NOT_RUN, and mutation `b` is `LEAKS` with an undeclared node where the serial arm says `PROVEN`.
The output is:

```
did not run in at least one arm: ['a']
compare: DID_NOT_RUN (1 line(s)) ...
rc=3
```

There is no `DIFFERS b:` line. This never produces a false 0, so the manager's "DNR → 3" rule holds.
But a verdict difference that was found is dropped from the output, and the exit code is 3, not the
protocol's 1 ("the thing the check exists to catch"). DID_NOT_RUN rows are what the worktree race and
kills produce. The operator will re-run for a clean pair, and an intermittent difference seen once is
then lost.

**Fix.**
- Always compute and print the `DIFFERS` lines over the mutations that ran in both arms.
- Recommended, and the manager's call: exit 1 when any such difference exists, else 3 on
  DID_NOT_RUN.
- Add a test with one DID_NOT_RUN row and one difference.

## Attack results (checked; no further finding)

1. **Lock coverage.** These are every worktree call in `scripts/` (grep for
   `"worktree"`/`worktree add|remove|prune|list|repair`):
   - the battery's are all in `battery_isolation`: `_registered` (list, which covers
     `_prune_unlocked`, `prune_shards` and `--prune-shards` at `mutation_battery.py:6660`, and the
     kept-shard check), `make_shard` (add) and `remove_shard` (remove), all via `admin_git`;
   - `battery_shards.py` and `battery_subset.py` issue no worktree command;
   - no prune or repair exists in the battery;
   - `orchestrator/dispatch.py:89-91`, `orchestrator/night.py:73`, `orchestrator/lint_brief.py:500-513`
     and `canary.py:261` add, remove or prune worktrees **without** the lock. The docstring discloses
     this (`battery_isolation.py:96-97`, "a worktree some other tool adds ... is not covered").

   Since 375f1ba such a collision is fail-closed: a failed add makes that shard DID_NOT_RUN, and a
   failed list in teardown is reported (modulo MINOR-1). The suite's tests that add worktrees use
   tmp repos (`test_orch_lint_brief.py:94-106` and others), not the shard's common dir.
2. **Lock file location.** `<git common dir>/rsr-worktree-admin.lock`, via `git rev-parse
   --path-format=absolute --git-common-dir` on `source`. `source` is always the invoking tree
   (`mb.ROOT`) or the stub, never a shard, so a `.git` *file* resolves to the main `.git`, and every
   shard of one repo names the same file (`test_the_lock_file_is_in_the_git_common_dir`). The real
   repo has no such file yet; the old code running in `_mgr` never creates it.
3. **Deadlock.**
   - No nesting: `admin_git` wraps exactly one `git()`, and `common_dir` runs before `flock`.
   - The order is always pool lock (non-blocking) → admin lock, and never the reverse.
   - The git child cannot inherit the fd: Python fds are non-inheritable (PEP 446) and
     `subprocess.run` closes fds.
   - SIGKILL closes the fd, which releases the `flock`.
   - The lock is not held across `uv sync` (`make_shard`: add, then release, then `sync_venv`).
   - Serialization cost: N short `worktree add`s at start and N removes at teardown. The repo has 736
     tracked files, no LFS-tracked paths and no hooks, so this is seconds per sharded run against
     hours. Estimated, not timed.

   *Observation, not graded:* the flock is blocking with no timeout, so a SIGSTOPped holder would
   wedge every other battery silently.
4. **Teardown hiding contamination.** It cannot hide it. Every mutation's `reset(shard)` runs
   `verify_clean` in the `finally` right after its suite (`mutation_battery.py:6745-6749`), so a dirty
   shard raises `Unisolated` before its row is appended. Teardown runs only after the last reset and
   only removes worktrees. A left-over worktree is reused next time only through the kept-shard path
   (checkout `--force`, clean, `verify_clean`). The residual problem is MINOR-1, which is fail-closed.
5. **`compare`.**
   - The exit codes match `rsr.exit_codes`.
   - `failure_reasons`-only differences give 0, and a verdict change gives 1 with `DIFFERS b: verdict:
     serial 'PROVEN' != sharded 'LEAKS'` (my case 1 and case 2).
   - List order counts (case 6 → 1). This is fail-closed, and rows are built sorted.
   - `None` vs a missing key, and bool vs int, compare equal (MAJOR-1).
   - `compare` checks nothing about SHA or table identity between the arms (the serial `--json` has
     neither), so "same SHA" is on the operator. Worth a line in the proof procedure.
6. **Anchors and inventory.** In-process `anchor_problems()` gives `[]`, with 396 entries and 396
   unique names (`review2-i2/anchors.log`).
   - Each of the 16 new gates matches exactly one test function, except the no-op-lock prefix gate
     `test_worktree_admin_`, which matches 3 by design.
   - Every declared off-gate node exists and has a reason.
   - The four new declarations (`i1: a DID_NOT_RUN row exits 0` → another-gate and `[False]`;
     `i1: the shard pool is never torn down` → the teardown test; `i2: a row for another mutation` →
     the another-gate test) each rest on an **observed** red:
     `I2-fix1.existing-vs-i2-files.log:1550,1563,1618` and
     `I2-fix1.proofs.recheck-declarations.log:63`. None rests only on reasoning.
7. **Report corrections (MAJOR-2 of the first review).**
   - The strikes at `I2-build.md:58, 125-127, 130-131` are honest. The 45-run claim is withdrawn.
     The stopped-driver red is conceded, with the cited lines.

8. **Ordering incident.** Nothing in the branch treats the 300-run 6-way e2e as a proof at 1b358d7:
   no commit message and no file in `scripts/`, `tests/` or `docs/` outside reviews mentions it.
   The report labels it "at 02edc5b ... before the hold" and lists the re-proof at the final head as

9. **Timing note for the later proof, not graded.** The deterministic admin tests hold the lock for
