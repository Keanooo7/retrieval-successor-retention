## Attack 2: `teardown` catches `(Unisolated, OSError)`

I traced both paths: teardown → `open_pool` `finally` → `_run_isolated` → `_report`,
and, per shard, `run_shard` → done record.
- Teardown runs after the last mutation's suite **and** its reset. Any loss of isolation
  during the run surfaces earlier, from `reset`/`run_suite` (Unisolated, which gives
  DID_NOT_RUN or a refusal). A failure only at teardown therefore comes after every
  verdict, and keeping the verdicts is right.
- `_Signalled` is a `BaseException` (`mutation_battery.py:6660`), so the new
  `except (…, OSError)` cannot swallow a stop signal. A signal during teardown still
  exits 128+N with no verdicts.
- The swallowed error **is** reported, as
  `SHARD TEARDOWN (verdicts kept; run --prune-shards): remove <path>: …` on stderr.
  Exit code and done record are unaffected by design. In a sharded `run`, that stderr
  goes only to the shard's log (`battery_shards.py:588-595`). It does not reach the
  driver's output or `summary.json`. That is an observation, not a finding: the
  cleanup is `--prune-shards`, and the prune catch has worked this way since round 1.
- **Gap:** see MINOR-1 and MINOR-2.

## Findings

### MINOR-1: the `OSError` half of both teardown catches is proven by nothing
- **Where:** `scripts/battery_isolation.py:478` and `:484`, and the mutation at
  `scripts/mutation_battery.py:6335`.
- **What I measured:** I narrowed both `except (Unisolated, OSError)` to
  `except Unisolated` in the scratch clone and ran the three I2/I1 test files. The
  result was **`passed=120 failed=0`**, rc 0. The narrowed code is green.
- **Why it matters:** the round-2 commit's own reason for catching rather than
  resolving the lock path once is that "the lock file's open() … [is] able to raise
  here". Only the `common_dir()` → `Unisolated` path is tested
  (`test_a_teardown_whose_admin_lock_cannot_be_resolved_keeps_the_verdicts`). The new
  mutation replaces the whole tuple with `KeyError`, so it cannot tell the two halves
  apart.
- **Fix:**
  - Add a test in which `worktree_admin_lock`'s `open` raises. For example,
    monkeypatch `iso.common_dir` to return a directory that does not exist, which gives
    `FileNotFoundError`. Assert that the verdicts are kept.
  - Add a mutation `except (Unisolated, OSError)` → `except Unisolated` for each of the
    two sites.

### MINOR-2: the new `remove_shard` docstring says other callers refuse, but they crash with exit 1
- **Where:** `scripts/battery_isolation.py:382-384`. The callers are
  `scripts/mutation_battery.py:6740-6743` (`--prune-shards`) and `make_shard` →
  `admin_git`.
- **What the docstring says:** "any other caller is before a verdict, where refusing is
  right".
- **What happens:** `--prune-shards` catches only `iso.Unisolated`. Demonstrated
  in-process in the scratch clone, with `iso.common_dir` patched to a missing directory
  and `mb.main` run with `--prune-shards`:
  - a `FileNotFoundError: … no-such-common-dir/rsr-worktree-admin.lock` traceback;
  - **rc=1**;
  - porcelain empty afterwards.

  Exit 1 is FAIL, not the DID_NOT_RUN (3) that a refusal is. The same holds for the
  serial battery at setup: `main` catches only `iso.Unisolated` around `_run_isolated`.
- **Status:** the behaviour dates from round 1, where `admin_git` entered
  `remove_shard`. This round only wrote the inaccurate sentence.
- **Fix, either:**
  - have `worktree_admin_lock` convert an `OSError` into `Unisolated`, which covers
    every caller at once; or
  - correct the docstring.

  Also, `--prune-shards`' "nothing removed" message is wrong when the raise comes after
  the first shard was removed.

### MINOR-3: `verdict_field_problem` checks list fields' type, not their elements
- **Where:** `scripts/battery_shards.py:405-407`.
- **What I measured:** these two files differ only in `off_gate`:
  - `[{"mutation":"a","gate":"g","verdict":"LEAKS","reddened_gate":true,"n_on_gate":1,"off_gate_allowed":[],"off_gate":[1],"off_gate_undeclared":[null]}]`
  - the same with `"off_gate":[true]`.

  `compare` exits **rc 0**, `compare: OK (0 line(s))`. So `True == 1` survives one
  level down, and `[null]` is accepted as a battery row.
- **Why MINOR:** no real row can contain these, since `_row` sorts node-id strings.
  This is residual hardening of review 2's MAJOR-1, not a regression.
- **Fix:** require `all(type(x) is str for x in v)` for `off_gate` and
  `off_gate_undeclared`. Require that each element of `off_gate_allowed` is a
  2-element list of `str`.

### MINOR-4: the serial-schema mutation's `why` is now stale
- **Where:** `scripts/mutation_battery.py:6013-6014`, and `scripts/battery_shards.py:324`.
- **What changed:** since e7f7144 every verdict field has its own check. The `absent`
  check therefore guards only `why` and `failure_reasons`. `compare` reads neither
  (`VERDICT_FIELDS`), and no reader in `scripts/` indexes either one (I checked
  `_markdown`, `battery_subset.py` and `battery_shards.py`).
- **Why that matters:** the entry's `why` still reads "so a serial and a sharded run
  can be compared field by field". The mutation no longer protects comparison.
- **Fix:** reword the `why` to what the check now protects: a merged record keeps the
  serial row schema, including I5's `failure_reasons`. If nothing is meant to depend on
  that, say so.

### MINOR-5: `VERDICTS` is a hand copy of `_row`'s four literals
- **Where:** `scripts/battery_shards.py:397`, against `scripts/mutation_battery.py:6853-6859`.
- **What could happen:** if a fifth verdict is added to `_row`, `compare` and the merge
  refuse real records with 3. That fails safe, never 0, but no test ties the two lists
  together.
- **Fix:** add a one-line test that collects the verdicts `_row` can produce from
  stubbed inputs and asserts the set equals `set(VERDICTS)`. Alternatively, export the
  tuple from `mutation_battery`.
