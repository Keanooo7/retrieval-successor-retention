## LB-4 (NEW, LAUNCH-BLOCKING, blocks 2a -- the run in flight): the F0 gate races the slot queue when fewer than 12 slots are granted

`preselect_gate` (`6c3adef`) requires `rc2.json` with exit 0 for **every** registered seed before a
seed's `select`. I recommended that "better still" in round 1, and I was wrong to say it "costs nothing".
`launch_2a.zsh` is unchanged: each seed's subshell waits only for its **own** R-C2 and fits.
`orchestrator.lanes.acquire` grants by polling, not FIFO. With fewer than 12 granted slots, which PM-3
now expressly allows (3–4 beside the battery), another seed's R-C2 can still be waiting for a slot when
a seed's `select` runs. That `select` then refuses ("R-C2 seed s: missing"):
- **no TUNE is spent for that seed**, which is good;
- but 2a's `finalize` is exit 3, a spurious control failure, which changes 2a's reading;
- and a relaunch would re-open TUNE for any seed whose `select` already ran.

A crude simulation (random poll winner, fits 10–66 min, R-C2 1 min) puts the probability of at least one
spurious refusal at about 25% with 3 slots and 34% with 4, about 8% with 5, and 0 with 9 or more. This is
not a measurement of this machine; it only shows the race is real.

**Immediate check for the in-flight 2a** (I did not touch `run3-2a-launch`): if
`runs/rsr-run3-2a/seed{0,1,2}/rc2.json` all exist with exit 0 now, before any `select` has started, the race
is moot for this launch. If any R-C2 is still queued, the risk is live.

**Fix:** in `preselect_gate`, wait (bounded) for another seed's `rc2.json` to appear and refuse only on a
present-and-failed one. Alternatively, have `launch_2a.zsh` run all three R-C2 to completion before any
fit or `select`. PM-3's statement that "results do not depend on how many slots are granted" does not
hold for this gate.
