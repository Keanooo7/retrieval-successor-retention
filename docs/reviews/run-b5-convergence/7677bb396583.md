## Findings

### MINOR-1: parent-side JSON writes are not atomic

`experiments/b5-convergence/run.py:1147` (measurements), `:1151`, `:1059`, `:1069`,
`:1096/:1120/:1174` (segments.json), and `Ledger.write`.

These are plain `write_text`. A kill during one of them leaves a truncated file. That
includes the SIGTERM handler's `SystemExit`, which is raised at an arbitrary
bytecode, possibly mid-write. On relaunch, `load_measurements` or `_read_json` raises
in `state()`, and the parent cannot start until someone deletes the file by hand. The
child checkpoints are safe; only the parent's records are exposed.

**Fix:** write every parent JSON through tmp + `os.replace`, as
`rsr.train.checkpoint` does. In the handler, set a flag and stop at the next
poll rather than raising mid-loop.

### MINOR-2: orphaning windows remain and nothing stops two writers

`run.py:1091` (children spawned) precedes `:1129` (handlers installed). A signal in
that gap, or an exception while spawning seed 1 or 2, orphans the children already
started. SIGKILL of the parent always orphans them, and launch 1 did exactly that. No
lock stops a relaunch while orphans are still writing the same seed directories: both
would write the same checkpoints and interleave beats.

**Fix:**
- Install the handlers before spawning.
- Take an exclusive `flock` or pidfile on `runs/b5-convergence/` and on each seed
  directory, and refuse to relaunch while it is held.
- Have the child exit when `os.getppid()` changes.

### MINOR-3: a control-5 record can be overwritten

`run.py:388`. The prior segment's record is renamed to
`resume_check.before-<new start stem>.json`, where `start` is the **new** segment's
checkpoint. Two relaunches from the same checkpoint (here: launches 1 and 2, both
from 3000) produce the same name. A third would `os.replace` over the earlier record
and lose a control-5 record. The name also mislabels which segment the file belongs
to.

**Fix:** name the file by segment index or timestamp, and refuse if the target
exists.

### MINOR-4: the run's three shas are not reconciled in one place

- The final ledger records `provenance.git_sha` b9595e0 with `dirty: true`. That is
  HEAD at write time: the author committed a status RESULTS into the running
  worktree at 08:05.
- The code the parent actually ran is a84f78d (segment 2), and the frozen manifest
  and `launch.json` carry 3d3e38b.
- a84f78d → b9595e0 changes no code, so the numbers are reproducible. But three
  shas for one run, and a dirty flag, are recorded without explanation in RESULTS.

**Fix:**
- Record the parent's start sha, `segments[-1].git_sha`, as the ledger provenance,
  or note it next to `provenance.git_sha`.
- Do not commit into a run worktree while its parent is live.

### MINOR-5: the manifest records `iters: 300`

`run.py:658`. `**S003.CONFIG` puts S0-03's `iters: 300` into the manifest, but this
run's iteration count is `cap` 9000. A reader of `manifest.json` sees a wrong
iteration count.

**Fix:** override `iters=CAP`, or drop the key.

### MINOR-6: the guard compares paths with `abspath`, not `realpath`

`run.py:267`. A symlinked out-dir that points into a protected directory passes the
guard. Separately, `Child.__init__` (`:410`, `:414`) creates the directory and opens
`train.log` before the child's guard runs. Every current caller guards the root
first, so there is no live hole.

**Fix:** `Path(path).resolve()` on both sides, and call `assert_writable` in
`Child.__init__`.

### MINOR-7: the parent's control flow has no tests

Untested:
- `verdict()`'s inconclusive branch (control 3, control 4, control 5, a raised
  measurement → exit 3);
- a relaunch skipping completed controls and not re-copying;
- the signal stop.

None of these is gated by a mutation. The five gated guards are the pure functions.

**Fix:**
- Add tests that feed `verdict()` fixture `root`s.
- Add a mutation on `if why:` in `verdict`, for example `if False:`.

### MINOR-8: the run used more threads than its lane claimed, and T0 is recorded outside the run

- **Threads.** The job took `--slots 12` for 3 × 4 child threads, but the parent
  measures at fresh-stream's 12 threads (`run.py:1027`, `:1143`) while the children
  train. The peak is 24 threads on a 12-slot claim. The results are unaffected,
  because the measurement is deterministic at a fixed thread count. The risk is to
  neighbouring cpu-det jobs.
- **T0 evidence.** PREREG control 1 (T0 at the start and at the end) is evidenced
  only in `~/Documents/.../reports/b5/T0-*.log`. Nothing is in `runs/` or the
  ledger.

**Fix:**
- Claim 24 slots, or measure between segments.
- Write the T0 rc and counts into `runs/<id>/` and the ledger.
