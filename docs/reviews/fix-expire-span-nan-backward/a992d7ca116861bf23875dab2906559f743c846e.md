## Q1. Is the fix numerically correct?

**Forward.** I compared the old expression and the new function on crafted inputs, bit for bit
(`int32` view, so signed zeros count).

Inputs where the two are bit-identical:
- ordinary rows;
- a batch containing an all-zero-weight row;
- a subnormal `total` (`0 < total < tiny`), where both give `a / tiny`;
- a `+inf` weight (both give NaN);
- `bfloat16` attention.

Inputs where the two differ:
- **NaN in `att` or `weight`, so `total` is NaN.** The old code outputs NaN. The new code outputs
  **0 for that row**, because `NaN > 0` is False. See F-1.
- **`total == 0` with a non-zero `a`**, which requires mixed-sign weights (e.g. `w = [1, -1]`).
  The old code outputs `a / tiny`; the new code outputs 0.
- **A `-inf` weight.** The outputs differ.
- **A `-0.0` weight.** The old code outputs `-0`, the new code `+0`.

**The last three are unreachable.** `weight = clamp(1 + r/R, 0, 1) · live · keep`
(`expire_span.py` `_weight`). It is always `≥ +0` and never `-0`. `att` is a softmax, so it is
`≥ 0`. Therefore `a ≥ +0`, and `total == 0` implies that every entry of `a` is `+0`. On every
reachable finite input, both versions produce `+0` for an empty row.

**Backward, rows with `total > 0`.** The `att.grad` and `w.grad` of every such row are
bit-identical between old and new, in the ordinary, empty-row-batch and subnormal cases.

**Backward, empty rows.**
- Old: `w.grad = [-inf, inf, -3.02e38, inf]`.
- New: exactly `0`.
- In the new code, `where` routes `+0` to `out`. Then `0 / clamp(total)` gives 0, and the
  `total` branch gets `-Σ(0 · a) / tc² = 0`. So no inf or NaN is created.

**FOLLOW-UP (5):**

1. **F-1: `total > 0` hides NaN in the forward pass.**
   - **What changed:** a NaN `total` now outputs 0, where the old code propagated NaN. The
     backward is still NaN.
   - **During training, E5 still catches it.** The loss stays NaN because the span loss computes
     `e · on_ramp = NaN · 0`.
   - **At VAL/EVAL there is no span loss.** A checkpoint with NaN `w, b` would give finite,
     memory-blind attention instead of NaN.
   - **When this can happen:** only if a NaN gradient lands on the final optimizer step, so that
     no later logged loss is NaN. The known source of such a NaN is removed by this fix.
   - **Fix:** a one-token change, `torch.where(total == 0, 0, out)`, preserves NaN propagation
     and is bit-identical everywhere else that is reachable. Alternatively, assert that the
     step-3000 `w, b` are finite in A2-C or E2.
2. **F-2: E5 checks only `loss` and `loss_lm`.** It does not check `es_grad_norm`, `es_bias`
   or the final checkpoint's `w, b`. This is pre-existing. Seed 1's signature (NaN
   `es_grad_norm` with a finite loss at step 130) shows that a NaN on the last step would pass
   E5.
3. **F-3: A2.2 wording.** Its heading "Tests (red without the fix)" covers both tests, but the
   bit-identity test passes at `c59d1af`. It is a non-regression guard.
4. **F-4: no battery mutation covers the new `where` guard.** Reverting it reddens test 1 (shown
   in Q3), so the guard is already caught by a test. This is battery coverage only.
5. **F-5: A2-C has no implementation at `a992d7c`.** That covers comparing all 18 seed-0/2
   heartbeats at every step 0–2999 and comparing the step-3000 `w, b`. It is DIAGNOSTIC, but it
   needs a script before RESULTS reports it.
