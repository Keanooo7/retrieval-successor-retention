## Findings

### MAJOR-1: the span loss is added to the loop's return value in eval mode

- `src/rsr/baselines/expire_span.py:250` computes `aux` whatever `training` is.
- `src/rsr/model/tg/policy_loop.py:366-370` adds it to `contrib` whatever `model.training` is.
- Reviewer probe, `model.eval()`, `torch.no_grad()`, same model, stream and spans:

```
eval mode, alpha= 0.0  loop return = 41.761993408203125
eval mode, alpha= 1.0  loop return = 119.13226318359375
```

Every eval path that reads `run_policy_loop`'s return as a loss would charge `α Σ e` to the
Expire-Span arm and to no other arm. That includes held-out loss and anything in `metrics/` or
`experiments/*` that calls the loop. The referendum's comparison would then be biased *against* the
baseline whose win ends the project, which is the direction B-3 forbids. [P7] Eq. 7 is a training
objective (P7:L330-335). The hook's own comment says the loss is added "rather than left to the
caller". That is right for training and wrong at eval.

**Fix:**
- Charge the span loss only when `training` is true. Either return `None` or a zero, or return it
  separately and have the train step add it.
- Add a test that the eval-mode loop return is identical for `alpha = 0` and `alpha > 0`.
- Add a battery mutation that re-adds it at eval.

### MINOR-1: rows past their stream length are still charged span loss

`expire_span.py:249-250` masks `on_ramp` by `mem_valid` only. `policy_loop.py:335-342` computes
`row_valid` but does not pass it. After a row's stream ends, its memories keep ageing through the
ramp and keep being charged. They receive no opposing LM gradient, because `step_fn` masks those
rows. The division is by the full `B`.

Reviewer probe, lengths `[10, 4]`. Per-row charge at t=4..7: row 0 `28.8 28.8 28.8 28.8`, row 1
`28.8 28.8 19.2 9.6`. Row 1 ended at t=4.

This is latent: `train()` uses `lengths = torch.full(...)` (`loop.py:570`). It becomes live for any
ragged-length caller, and after MAJOR-1 is fixed, for any ragged training.

**Fix:** pass `row_valid` into `memory_weight` and multiply `on_ramp` by it.

### MINOR-2: the `on_write` contract text is stale after the merge with night (known)

- `expire_span.py:65-68` says `run_policy_loop` passes `on_write` "the victim index ... and is 0 for
  a row that was not full".
- ADR-0010 `:74-76` says the same.
- On `night/2026-09-30` the loop passes `newcomer_slot(...)` and asserts that the slot holds step
  `t`'s write.

The policy's no-op `on_write` stays correct. Only the prose is false.

**Fix:** reword both passages to the new contract (the newcomer's landed index). Keep the
"recomputed from the occupant" argument, which still holds.

### MINOR-3: "Aux loss form: MATCH" overstates, and the per-ramp-step scale is only in q3

ADR-0010 `:35` and `expire_span.py:30-35` present Eq. 7 as matched. As implemented, each memory is
charged `α·e` at each of about `R` ramp steps. Eq. 7 charges `Σ_i e_i` once (P7:L330-335). ADR-0010
q3 (`:188-191`) raises this honestly. The table row and the module docstring should agree with it.
While both `α` and `R` sit in the q2 grid, `α`'s effective scale is coupled to `R`.

**Fix:** change the table row to "form matches §4.2's timing; scale vs Eq. 7 open (q3)". Add the
same sentence to the docstring. No code change unless Brendan rules q3.
