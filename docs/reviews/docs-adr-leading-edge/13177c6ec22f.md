## Findings

### MAJOR-1: comparator-defining choices are classed TECH, against the red-team finding the ADR cites

ADR-0011 `:382-386` classes these as TECH:

- **Q7:** filler argument coding.
- **Q8:** query arguments and object identity.
- **Q10:** graph construction beyond p. 379.
- **Q11:** the survival convention for E7's three numbers.

In practice, an agent would settle each of them in the implementing PR. The ADR's stated authority
for existing, REDTEAM-v2 X-3 (`:58`), says otherwise (`REDTEAM-v2.md:81-82`): "This choice is
expensive to reverse, because it defines the named comparator. It is not TECH-DECIDE", and asks for
"an ADR for the **propositionalisation** and the s↔M mapping, **for Brendan**."

Q7 and Q8 *are* the synthetic propositionalisation. The ADR's own §3 consequence 1 (`:313-315`)
shows that Q7 changes the graph: under literal coding, repeated fillers overlap. Q10 is the graph.
Q11 fixes the convention for correction 25's primary E7 number.

**Fix:** reclassify Q7, Q8, Q10 and Q11 as OWNER-ONLY, or as "proposed default, OWNER-RATIFY".
Q9 (constructor shape) can stay TECH.

### MINOR-1: "E0g already picked NFRD" overstates the status

ADR-0011 `:96-98` says "E0g already picked NFRD" (and C7-ADR.md repeats it). E0g is PASS
(`RESEARCH-CONTEXT.md:512`), but the stimulus set is ADR-0005, which is **proposed, pending owner
sign-off and the "in hand" exit** (`RESEARCH-CONTEXT.md:577`).

**Fix:** "ADR-0005 (proposed, pending owner sign-off) names NFRD".

### MINOR-2: Q6 pre-answers an OWNER-ONLY item and misattributes a docstring

- **Pre-answer.** `:381` reads "This ADR says no", and D6 `:195-201` argues the same. Q6 is marked
  OWNER-ONLY. Stating a proposal is legitimate in a PROPOSED ADR. The table row, however, should
  pose the question, not answer it.
- **Misattribution.** The same row says the evicted graph "is retained per `MemoryState`'s
  docstring". The docstring (`policy.py` on night, `accum` and `row`, ~:70-83) says cross-step state
  lives on the policy, keyed by row and occupant. It says nothing about retaining evicted nodes.
  That retention is D8's own proposal (`:264`).

**Fix:**
- Reword Q6 as "Is a reinstatement analogue ever in scope? (D6 proposes no: it changes the write
  path, §3.1 and E0b.)"
- Cite D8, not `MemoryState`, for graph retention.

### MINOR-3: the red team is described as ruling, and its source is outside the repo
