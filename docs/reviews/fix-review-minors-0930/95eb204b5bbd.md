## Findings

### MINOR-1: an agreeing tie is still decided by sha order; the doc says it never is

- `docs/review-records.md:75-78` says a tie "is never broken on the file name".
- `scripts/orchestrator/merge.py:355` does `_, path, fm = tied[0]`, and `tied` is
  sorted by path (`<reviewed_head[:12]>.md`).
- When the tied records agree, that record's `reviewed_head` is the staleness
  anchor. So the same history shape gives 0 or 3 depending on sha order.

Reproduction (`synth_agree.py`): two MERGE records on parallel lines, with code only
on line B, merged:
```
('A sorts first', 3) review is stale: docs/reviews/eng-x/475cc137728b.md (reviewer rev-a) covers 475cc137728b, but 475cc137728b..f24cc92d3a82 changes non-exempt paths: b.py -- re-review at f24cc92d3a82; not merged
('B sorts first', 0) docs/reviews/eng-x/e682e6014025.md
```

It is never fail-open. An accepted anchor means head's tree equals that
record's reviewed tree plus exempt paths only. The cost is a false refusal half the
time, which contradicts the sentence the branch added.

**Fix (either):**
- run the staleness diff against every tied anchor, and accept if any one of them
  shows only exempt paths;
- or reword `review-records.md:77` to say that agreeing tied records are anchored on
  the first by file name, and that the result may be a false "stale".

### MINOR-2: stale wording left beside the edits

  branch edited, still says a record passes with "MERGE (or MERGE WITH FIXES with
