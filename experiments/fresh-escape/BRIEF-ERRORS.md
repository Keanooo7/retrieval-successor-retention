## Corrections after the independent verifier's report (verdict CONFIRMED-WITH-CORRECTIONS; the classification is unaffected)

The verifier recomputed R, C, `P` and the classification from the per-seed samples and found no mismatch. It re-measured one ckpt-009000 and all three start checkpoints from scratch and matched exactly, and it recomputed every stream-loss window from the heartbeats and matched `stream_answer_loss_window_means` exactly. Its full report, with the numbers, is `~/Documents/RSR-2026-09-26-overnight/VERIFIER.md`. The bullets above stand as written; these corrections apply to them:

- "zeroing the memory changes nothing for queries whose answer has been evicted" is overstated. Only the accuracy is exactly equal; the `gap_gt_M` Brier score differs very slightly between live and zeroed on every seed. Read it as: in that bucket, no answer's correctness changes when the memory is zeroed.
- "Both conditions sit at the level of the start checkpoint" is loose. Compare `A.ckpt9000.heldout.live.all.answer_acc` and `A.ckpt9000.heldout.live.gap_gt_M.answer_acc` with the `A.ckpt3000.*` keys of the same names in runs/fresh-stream/ledger.json: individual seeds moved both up and down, but live and zeroed both stay within a narrow band around the uniform-guess accuracy of one in sixteen.
- "the earlier checkpoints' `R_quantity` values move both ways around zero" holds for the third seed only. On the first two seeds `R_quantity` is exactly zero at every checkpoint from 4000 to 8000. At 9000 the small positive value amounts to about one query per bucket per seed.
- "Every window stayed on the plateau fresh-stream's arm A reached" overstates the flatness. The slow downward creep continued: every window in the last thousand steps is lower than every window of fresh-stream's arm A over its last thousand steps. The creep is tiny, however: every window stays above the loss of a uniform guess over sixteen answers, and far above `stream_loss_threshold`.
- "never crossed `stream_loss_threshold` at any step": the conclusion holds, but the ledger key cited is window-level. The verifier's per-step minima from the heartbeats (in VERIFIER.md) support it directly: no single step on any seed came near the threshold.
- The paragraph on the mutation battery was not verified by the verifier; its source is the battery log `~/Documents/RSR-2026-09-26-overnight/battery.log`.
- Record gap, not a prose error: the first control's re-measured values are not stored (the ledger keeps only `control_1.max_abs_diff`), so that control can be audited only by re-measuring. The verifier did so for all three seeds and matched exactly.
